# 階段 2 計畫：項目進度與預警看板（系統 1）

狀態：**待確認**（確認後才開始實作）
依據：CLAUDE.md、docs/specs/progress.md、公司現有的項目看板（2026-10-05 版，存在 `data/raw/`，不提交）
估計時數：8–10 小時（超過 15 小時會停下來回報）

> 本文件只描述現有看板的**結構和統計數字**，不寫客戶名稱、人名或案件內容（CLAUDE.md 第 4 節）。

## 1. 先講結論：規格和公司實際的看板不一樣，需要你決定

規格（docs/specs/progress.md）假設有三個檔案：項目清單、里程碑、更新紀錄。但公司實際用的是**一個 Excel、一張「項目看板」分頁**，一案一列，由專案組會議紀錄整理而來。

| 規格假設 | 現有看板實際情況 |
|---|---|
| 每案有 project_id | **沒有編號**，只有「客戶／案子」名稱（58 案，沒有重複） |
| 有起始日、預計結案日 | **沒有**；只有「下一個日期」（下一步要做的日期） |
| 有里程碑檔（預計日、實際完成日） | **沒有**；只有「近期下一步」一句話 |
| 有更新紀錄檔（更新日） | **沒有**；看板整份是某次會議的快照 |
| 狀態：未開始／進行中／已結案／暫停 | 階段：規劃中／洽談中／進行中／卡關／結案中／已完成／暫緩（有下拉選單） |
| 負責人一欄一人 | 負責人是自由文字，常有多人或括號說明（例如「甲（與乙）」「甲／乙／丙」） |

另外，現有看板**已經用公式算出**：各階段案數、7 天內到期數、已過日期未完成數，並用顏色標出卡關與逾期。

所以這個系統**不應該**要主管改成三個檔案（違反「輸出放在使用者已經在用的地方」「不要過度設計」）。建議改成**直接讀現有看板**，並把規格的預警規則改寫成看板上真的有的欄位（見第 4 節）。這等於修改規格，依 CLAUDE.md 第 6 節要先問你。

## 2. 用現有看板試算的結果（基準日 2026-10-14）

| 項目 | 數字 |
|---|---|
| 案件總數 | 58（進行中 25、洽談中 10、規劃中 10、結案中 6、已完成 5、卡關 1、暫緩 1） |
| 已過「下一個日期」但未完成 | 10 案 |
| 7 天內到期 | 4 案 |
| 卡關 | 1 案 |
| **沒有填「下一個日期」** | **40 案（69%）**，其中進行中、結案中、卡關的就有 20 案 |
| 有寫卡點／風險 | 20 案 |

最值得主管注意的可能不是逾期，而是**七成的案子沒有下一步日期**，系統無法判斷它們是否會延誤。這會放在報表第一句之後。

另外，看板是 10/5 的版本，到 10/14 已經 9 天沒更新，「已過日期」的 10 案有些可能其實已經做完了。這正是需要「與上週比較」的原因。

## 3. 這個系統比現有看板多做什麼（避免重工）

| 現有看板已經有 | 系統另外補上 |
|---|---|
| 各階段案數、7 天內到期數、逾期數 | 每一條預警都寫明「為什麼」和「建議跟誰確認」 |
| 卡關、逾期上色 | **與上週比較**：新增的預警、已解除、持續中 |
| — | **長期沒有變化**：同一案連續幾週下一步、日期、階段都沒變 |
| — | **資料品質**：缺日期、案名重複、日期格式錯、階段不在選單內 |
| — | 負責人同時負責的案數（只列事實，不排名） |
| — | 一頁 md 摘要＋給管理層週報讀的 summary.json |

如果你覺得現有看板已經夠用，第一版也可以只做「與上週比較」和「資料品質」兩項，時數約減半。

## 4. 建議的預警規則（門檻放 config/thresholds.yaml，都標「待主管確認」）

| 代號 | 規則 | 燈號 | 對應規格 | 說明 |
|---|---|---|---|---|
| P01 | 「下一個日期」已過，且階段不是「已完成」 | 紅 | A01 | 與現有看板的「已過日期未完成」算法一致 |
| P02 | 「下一個日期」在 N 天內（含今天，起始值 7），且階段不是「已完成」 | 黃 | A02 | 與現有看板的「7 天內到期」一致 |
| P03 | 階段是「卡關」 | 紅 | 新增 | 現有看板已用顏色標出 |
| P04 | 同一案連續 N 天（起始值 14）「階段、近期下一步、下一個日期」都沒變 | 黃 | A03 | 要有兩週以上的快照才能算；第一、二週顯示「待補：快照不足」 |
| P05 | 同一位負責人負責的進行中案子超過 N 個（起始值 5） | 黃 | A04 | 只列「負責人＋案數」，按姓名排序，不排名、不評價 |
| — | 進行中、結案中、卡關的案子沒有「下一個日期」 | 資料品質 | A06 | 不算預警，列在資料品質分頁 |
| — | 案名重複、日期格式錯、階段不在下拉選單內、必填欄空白 | 資料品質 | A06 | 同上 |

規格的 A05（結案逾期）**拿掉**，因為看板沒有預計結案日。

## 5. 輸入
- `data/raw/` 下的看板 Excel，讀「項目看板」分頁。標題列用名稱「客戶／案子」自動找，不寫死第幾列。
- 新增 `config/progress_columns.yaml`：把看板的中文欄名對應到系統欄位，看板欄名改了只要改這個檔。
- 案件的識別用「客戶／案子」名稱，因為看板沒有編號。**案名一改，系統會當成一案消失、一案新增**，報表會列出來提醒。
- 不讀「待辦事項」「後續追蹤項」「角色切入點」三個分頁（見第 8 節第 3 點）。
- 原始檔只讀不改。

## 6. 輸出（放 data/out/progress/）
| 檔案 | 內容 |
|---|---|
| `進度看板_YYYYMMDD.xlsx` | 總覽（三句結論、紅黃綠數量）、預警清單（案子、規則、為什麼、建議跟誰確認）、項目明細（依燈號上色）、本週變化、負責人案數、資料品質 |
| `進度摘要_YYYYMMDD.md` | 一頁摘要，第一句講結論，例如「本週有 11 案需要注意：10 案已過下一步日期、1 案卡關」 |
| `summary.json` | 給管理層週報讀（格式同 docs/specs/digest.md） |
| `data/interim/progress_snapshot_YYYYMMDD.csv` | 本週快照，給下週比較用 |

每份輸出都有頁首資料等級、頁尾（資料截至日期、輸入檔、執行編號、待補清單、計算方法）。

## 9. 需要你確認的事
1. **同意改規格嗎？** 直接讀現有看板、規則改成第 4 節的 P01–P05、拿掉 A05。同意的話我會一併更新 docs/specs/progress.md。
2. **資料等級。** 規格寫「內部一般」，但看板的「卡點／風險」「備註」有客戶未公開的資訊（例如客戶明年是否續約的考量）。依 CLAUDE.md 第 4 節，不確定時當作「客戶機密」。建議：
   - 整份看板與系統輸出標「客戶機密：僅執行長與主管」；或
   - 輸出不放「卡點／風險」「備註」兩欄，維持「內部一般」。
   這個系統不用大模型，等級只影響頁首標示、存放位置，以及之後週報的等級。
3. **其他三個分頁要不要納入？** 「後續追蹤項」有檢查日期和狀態，也能算逾期；「待辦事項」是個人待辦。建議第一版**不納入**，只做項目看板。
4. **負責人怎麼算案數？** 建議只算括號外的人名（「、」「／」分開的都算），括號裡的協作者不算；「行政」「全體專案人員」這類不是人名的不算。用 10/5 版試算，目前沒有人超過 5 案。
5. **「進行中」的範圍。** P05 和資料品質的「應該要有日期」建議算進行中、結案中、卡關三種。洽談中、規劃中要不要也算？
6. **你說「可以把內容寫進去」，是指哪一種？**
   - 甲：讓系統讀真實看板、在本機產生真實報表（報表在 data/out/，不提交）。**我已經把檔案放到 data/raw/，這個可以直接做。**
   - 乙：把客戶名稱、人名、案件內容寫進**提交到 GitHub 的檔案**（計畫、測試、假資料）。這和 CLAUDE.md 第 4 節「絕不把真實資料、真實客戶名稱提交到程式倉庫」衝突，而且進了 git 歷史就很難刪乾淨。如果確定要這樣做，請明確告訴我，我會先修改 CLAUDE.md 的這條規則再做。
   目前這份計畫照甲的方式寫，只寫結構和統計數字。
