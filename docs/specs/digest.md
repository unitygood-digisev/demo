# 規格：管理層週報／月報（系統 5，src/digest）

目標：一頁讓執行長和主管看懂本週全局，不用開會前臨時整理。
原則：週報只讀其他系統的摘要檔，不讀原始資料。

## 標準摘要檔（每個系統執行後都要寫一份 data/out/<system>/summary.json）
```json
{
  "system": "progress",
  "run_id": "...",
  "as_of": "YYYY-MM-DD",
  "classification": "內部一般",
  "headline": "本週有 3 個項目可能逾期",
  "metrics": [{"key": "...", "label": "...", "value": 0, "unit": "...", "prev_value": 0, "source_ref": "..."}],
  "alerts": [{"level": "紅", "rule": "A01", "why": "...", "subject": "...", "suggested_owner": "..."}],
  "data_quality": ["..."]
}
```

> 2026-10-14 補充（依 docs/decisions/phase4.md）：
> - 讀哪些系統、摘要檔路徑、是否已上線、一頁限制都在 `config/digest.yaml`；財務的摘要檔可用環境變數 FINANCE_OUT_DIR 指向公司資料夾。
> - 已上線系統不足三個時，結論第三句是狀態句（哪些系統未更新／尚未上線、資料品質共幾項）。
> - 系統標為未上線時顯示「系統尚未上線」（指標表只一行），不算「未更新」。
> - 摘要檔格式錯誤、日期晚於週報日期時「未納入」並列出原因。
> - 一頁：以版面估算（每段依換行數計）限制內文，超過時依序截短資料品質 → 外部情報 → 需要決定的事項；並以 LibreOffice 轉 PDF 測試確認 1 頁。

## 輸入與設定
- config/metrics.yaml：管理層選的 5–8 個指標（key）與顯示順序。沒有由管理層指定前，用起始版並標「待確認」。
- 窗口：週報的「上週」以 prev_value 為準。

## 版面（一頁內，字數上限在 config）
1. 本週結論：三句，由模板從 headline 組成，不用大模型改寫。
2. 關鍵指標表：本週／上週／變化。
3. 需要您決定的事項：紅色預警前 5 條，每條一句話，寫明為什麼和建議跟誰確認。
4. 外部情報前 3 則（標題加連結）。
5. 資料品質提醒。

## 規則
- 週報的資料等級 = 所有輸入摘要檔中最高的等級，標在頁首。
- 某個系統的摘要檔缺失或超過 N 天（config）沒更新，要在週報寫「該系統本週未更新」，不要省略。
- 預設不呼叫大模型。若之後要加，只能在所有輸入都是公開或內部一般、且我明確同意時才行。
- 輸出格式：.docx 和 .md，另加一份可貼到郵件的純文字版本。不自動寄出。

## 驗收條件
- 週報中的每個數字都等於來源 summary.json 的值（測試）。
- 一個系統缺失時照常產生週報，並有「未更新」提示。
- 頁首等級標籤等於輸入中的最高等級（測試）。
- 重跑結果相同，長度不超過一頁。
